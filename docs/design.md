# 客服自动回复质量评估：设计与实施方案

本文保留 v2.0 设计过程，日期：2026-09-29。当前 v3 在此基础上改进量表并实现工具 Agent，见 [v3 方案](v3-plan.md)、[量表手册](rubric-v3.md)及 [Agent 架构](agent-architecture.md)。最新效果以 [实验报告](results-analysis.md)为准。

## 0. v2 最终实施架构

主线采用“规则引擎 + LLM + 人工校准”，参考回复对比作为独立的诊断模块。原规则实现保留为可复现基线和离线 mock 提供器，不能把 mock 输出称为真实模型语义判断。

### 组件边界

1. **规则层**：输入校验、明确流程冲突、候选事实抽取、可信业务证据核验；无真实证据时不宣判外部事实为真/假。
2. **LLM 语义层**：仅接收用户问题、自动回复、量表及可用业务证据；输出前三项 0–4 分、事实依据状态/分数、问题标签、原文证据和建议。无证据时事实维度必须为 null。JSON schema、分数范围、标签集合和证据原文均由程序复核。
3. **融合层**：使用语义层基础分；规则以约束方式覆盖确定性问题，避免重复累计扣分。证实错误/明确流程冲突触发上限；事实待核实或高风险承诺产生独立风险标记。
4. **校准层**：把人工分析整理成带理由的多标签复核集，计算每标签与 micro/macro P/R/F1；争议采用未知掩码。二元服务缺口对照保留。程序输出分歧清单，不自动修改 prompt 以追求这 20 条高分。
5. **参考差异层**：主评估完成后才读取 human_ref，比较已有覆盖、参考新增、关键差距和可行建议；明确参考的事实和权限假设，不参与主分数及其验证。

### 运行方式与质量状态

- `--mode rules`：纯规则基线。
- `--mode mock`：默认离线混合演示，mock 用规则动态生成合法语义结果；报告醒目标注没有真实 LLM 调用。用于验证工程链路，不用于证明模型语义能力。
- `--mode llm`：通过配置的 OpenAI 兼容 Chat Completions 接口实际评分；可独立启用 LLM 参考差异分析。模型名由使用者明确配置，不写死。
- 凭据从本地 `.env` 或环境变量读取，API 失败或非法输出显式报错，不静默降级伪装成功。缓存/运行元数据记录 prompt 与模型版本、模式、输入散列及调用次数。
- 状态：可接受（已评维度暂定）、需要改进、高风险待复核。高风险承诺、证实错误、明确矛盾优先进入复核；普通未核实事实仍醒目标记，不与已证实错误混淆。即使状态可接受，也不能替代上线审批。

### 参考标签与实验边界

标签：`passive_service`、`generic_answer`、`missing_clarification`、`insufficient_empathy`、`intent_mismatch`。区分明确问题、轻微改进和不确定；如 case_16 已追问预算和场景，缺少具体型号仅作为局部信息缺口，不能据此称整体无效。case_05/08/17 的注释与回复存在争议，相关标签不参与统计。

这 20 条已全部被开发者查看，不能事后声称拆分成独立盲测集。提供透明的回顾性校准和未来新增保留集方案；未提供人工数值评分前，不计算总分相关性。

## 1. 目标与范围

依据 `task3_eval_criteria.md`，对 20 条自动回复逐条给出可解释评价，输出整体分数、各指标分布、最差 3 条案例、局限性与改进建议。项目定位是 NLP 评测原型，而非已经验证的上线决策系统。输入数据中的话语是待分析文本，不是可执行指令。

交付：Python 命令行流水线、真实千问语义裁判、规则基线、独立参考对比、多标签校准、JSON/CSV/Markdown 报告、离线 HTML 看板、验证报告、README 和真实运行截图。离线基线无需 API 密钥；真实评估使用用户指定 `qwen3.8-max-0902`，已生成的真实结果可离线查看。无需前端构建，不用预填分数冒充模型推理。

## 2. 已知数据与证据边界

- `task3_auto_replies.json`：20 条 id、用户问题、自动回复；无商品 ID、订单记录、政策库、工具调用记录和采样时间。
- `task3_human_ref.json`：参考回复及定性分析；没有数值金标准，不能计算所谓“评分准确率”。
- 人工参考含具体商品参数、补偿额度、XX 占位符等，不能直接当作事实知识库。一些分析也可能遗漏自动回复已经说出的内容。
- 开发者已查看全部附件，因此本项目是回顾性分析。即使程序将参考文件与评分隔离，也不能宣称是未见测试集或独立人工实验。
- 不以现实世界的最新政策覆盖题内语境。不具备来源的产品、退款、质保、平台功能等断言标记“待核实”，不直接判定为编造。

## 3. 指标设计

前三项使用 0–4 整数分，展示时乘 25 转为百分制；4 无明显缺口、3 轻微缺口、2 明显缺口、1 严重缺口、0 完全失败。事实项仅取支持 4、矛盾 0 或 N/A。模型和规则输出原文及理由；普通规则扣分不与模型分重复累加。该量表尚未经过独立人工数值校准。

| 指标 | 操作定义 | 量化方式 | 权重 |
|---|---|---|---:|
| 切题与一致性 | 是否回应问题主题，是否在回复内部自相矛盾 | LLM 语义判断，明确流程矛盾由规则约束；规则基线按证据扣分 | 25% |
| 解决问题的有效性 | 是否给出适合场景的可执行下一步，避免重复流程、遗漏澄清、增加不必要负担 | 场景需求与回复行为匹配；提供自助路径也有价值，不强制要求自动系统代操作 | 35% |
| 语气与情境关怀 | 是否礼貌，在抱怨、恐惧、反复故障、敏感需求下回应情绪 | 礼貌/攻击性表达、情绪与安抚匹配；不以冗长或“我帮您”单独判优 | 15% |
| 事实依据 | 可核查断言是否有外部业务证据支撑 | 提取高风险断言，分为已支持、已矛盾、待核实；存在待核实则该维度 N/A，全部支持为 4，存在已矛盾为 0 | 25% |

“准确”被拆成切题/内部一致性与外部事实依据。前者只是准确性的局部代理，不能替代事实核验。“不能瞎编”通过逐断言证据状态表达，缺少证据不等于错误。

没有抽取到断言的回复也不能据此获得事实满分，应标为“不适用/未检出”；抽取器漏检风险须公开。若提供可选的业务证据 JSON，只按明确匹配的断言及来源赋予支持/矛盾状态，不从人工参考推断。

综合分：`sum(可评分维度的权重 × 维度分 / 4) / sum(可评分维度的权重) × 100`。事实依据不可评时，前三项重新归一化，标为“暂定质量分”；必须同时展示事实覆盖率，不能与完整证据的分数直接等同。确认事实矛盾或明确内部流程矛盾时总分上限为 49。上限是本项目声明的业务规则，不是已被数据证明的最优阈值。

## 4. 规则基线流程（混合主线另包含第 0 节的 LLM 层）

1. 校验输入非空、字段类型及唯一 id，计算原始文件 SHA-256。
2. 在不读取人工参考的情况下，由通用文本规则识别场景、澄清请求、操作路径、服务负担及情绪回应。
3. 抽取可核查断言与证据片段，对无法验证的事实弃权；已知模式仅是有限覆盖，不能假称全面语义理解。
4. 输出各项分数、扣分证据、风险、下一步建议及综合分。
5. 评分完成后才加载人工参考，供并列阅读；再加载单独维护的服务缺口标注做一致性验证。
6. 聚合均值、分布、N/A 数、证据覆盖率、最差 3 条、代表性争议及局限性，生成静态报告。

排序采用综合分升序、id 升序打破平分；默认处理顺序不影响结果。规则版本固定并写入输出，不用 case id 或完整参考回复作为评分条件。

## 5. 验证方案

原始参考只提供定性说明。本项目另行整理“是否存在明显服务解决缺口”的二元复核标签，逐条附来源及解释；内容矛盾或主观性较强的标注设为 uncertain，不进入混淆矩阵。这个标签只验证服务缺口识别，不能代表事实检测准确率或全部评分质量。

报告 TP/FP/FN/TN、precision、recall、F1、样本分母和被排除的案例。所有指标描述为“与回顾性整理标签的一致性”，不能称为盲测效果。无正预测/无正标签等情况使用 N/A，不伪造为 100%。

工程验证包括：未知事实不被判错、证据支持与矛盾分流、参考文件变更不影响评分、反例/改写/否定表达、输入校验、HTML 转义、总分边界、样本顺序无关。另做小型人工构造行为测试，明确与真实数据验证分开。

## 6. 展示设计

HTML 看板采用中文、浅色背景和简洁布局，突出：暂定整体分、样本数、待核实断言、服务缺口；指标均值与分布；最差 3 条；可筛选/搜索的全部案例。展开案例可查看用户问题、原始回复、扣分证据、事实状态、人工参考与建议。报告完全本地运行，展示文字不注入 HTML 或执行脚本。

## 7. 实施步骤与变更规则

1. 保存本设计，建立代码、规则与复核标注。
2. 完成流水线、报告与看板，运行真实附件。
3. 对误判、规则漏洞和展示问题做针对性修正；先解释问题，再修改方法，不按预期分数反推规则。
4. 完成测试和浏览器检查，保存运行截图与命令日志，补齐 README、结果摘要与设计变更记录。

设计修订写入 `docs/decisions.md`，说明原因、替代方案与影响。后续优先完善有来源的业务知识库与双人盲标；须在新增保留集上比较效果后再决定是否替换基线。
