# v3：先改进评价标准，再实现客服质检 Agent

## 改进目标

旧版主要问题：把“可选增强”当“明显缺口”；中性咨询也要求道歉；标签边界重叠；没充分区分用户要流程还是已卡在流程。优先改进量表的可操作性，不修改旧标签来制造更高分。

## 阶段一：评价标准

1. 冻结 v2 提示词、真实结果与人工标签。旧结果存入 experiments，旧代码可由 Git 提交 b8bf47c 复现。
2. 先判断用户诉求、已有信息、是否显著需要安抚，再逐维评分；把“判断错问题”“无法推动解决”“语气问题”分开。
3. 细化 0–4 分锚点，给每类问题定义正例条件、反例、轻微/明显严重程度和标签共现条件。对中性咨询不要求模板道歉；有效澄清也是解决行动。
4. 保留原有事实弃权、风险门控、参考隔离，不把没有业务证据伪装成事实已验证。
5. 在相同的 20 条数据、相同冻结标签上报告修订前后 P/R/F1、分数变化和分歧；额外运行预先声明的人工构造对照样例，检查中性语气、澄清、卡点、未知事实、回复指令干扰等行为。构造集只是开发测试，不是独立真实业务盲测。

不以本次样本上的指标提升证明泛化能力；不反复挑选最优一次输出来报告。若修订仍有不足，保留真实结果并写明。

## 阶段二：Agent 形式

构建一个面向客服主管/质检人员的本地 Web 助手，复用千问模型作为调度器。采用受约束的“思考任务 → 选择工具 → 执行 → 观察 → 继续/回答”循环，展示简短计划与工具轨迹，不展示模型隐式推理。

工具范围：查看数据集、查看评分量表、读取评估汇总、筛选案例、展开原文与证据、查看校准分歧、执行批量评估、在当前会话暂存有来源的事实核验结论并重新计算、导出当前会话报告。复核结论属于操作者提供的证据，Agent 不自行捏造来源。

会话上下文保存当前数据集、选中案例、当前评估结果、待核实项和工具轨迹。上传 JSON 只进入受控数据集目录；不让 LLM 读取任意本机路径、密钥或执行 shell。HTTP 仅监听本机，文件下载限定报告白名单。错误与离线演示显式显示，不冒充真实执行。

支持示例：“分析这批回复并生成报告”“为什么这个案例得分低”“哪些承诺需要核实”“现有结果能支持扩大覆盖吗”“这条政策已有来源，重新计算影响”。

## 验收与发布

实际模型完成新版 20 条评估及行为测试；运行 Agent 多轮工具调用、上传/校验、证据更新、报告导出及浏览器交互；保留关键截图、测试和实验报告。先验证评价标准，再启用 Agent。最后提交 GitHub 同一仓库，保留旧版并标记 v3.0.0。
